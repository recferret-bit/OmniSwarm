# OmniSwarm audit: W10 (review registry), W11 (landing app), W13 (agent guard)

Branch `review/full-pass` at `8fd7065`. Read-only audit. No NEAR RPC, no wallet, no testnet deploy, no provider calls, no keys read.
Method: (1) static pass, where each issue row's gate is checked against code or tests; (2) dynamic pass, where every gate command was run. Frontend, guard and demo commands ran in a scratch mirror (`.../scratchpad/mirror`, with `node_modules` symlinked). That kept the tracked `frontend/landing/dist/` from being rebuilt in place and stopped `demos/attack/run.mjs` from rewriting `demos/attack/attack.log`. Registry metadata (`npm view`, `cargo search`, and the `near-api-js@7.4.0` tarball unpacked into scratchpad) was read to check the library claims.

## 4. Gaps to fix (ranked)

1. **Deploy script cannot produce a working operator (W10-09).** Every operator call would fail on testnet. Fix in `deploy-testnet.sh`:
   ```sh
   cargo near build non-reproducible-wasm --manifest-path contracts/review-registry/Cargo.toml
   near account create-account fund-myself $CONTRACT '5 NEAR' autogenerate-new-keypair save-to-keychain sign-as $OWNER network-config testnet sign-with-keychain send
   near account create-account fund-myself $OPERATOR '2 NEAR' autogenerate-new-keypair save-to-keychain sign-as $OWNER network-config testnet sign-with-keychain send
   near contract deploy $CONTRACT use-file $WASM with-init-call new json-args '{"owner":"'$OWNER'","operator":"'$OPERATOR'","treasury":"'$TREASURY'","price_yocto":"1000000000000000000000000"}' prepaid-gas '30 Tgas' attached-deposit '0 NEAR' network-config testnet sign-with-keychain send
   near account add-key $OPERATOR grant-function-call-access --allowance '1 NEAR' --contract-account-id $CONTRACT --function-names 'mark_running, attest, refund' autogenerate-new-keypair save-to-legacy-keychain network-config testnet sign-with-keychain send
   ```
   Confirm the flag spelling against the installed near-cli-rs `--help`. Then delete the contract account's full-access key, or document who holds it (a holder can redeploy arbitrary code, which undermines the guard). List only methods that exist. Add a dry-run test asserting `operator` in `new` equals the account receiving the FC key.
2. **The guard trusts an unproven `deployed` binding (W10-04 × W13).** Anyone can request a review of a benign repo with `deployed = <malicious contract>`. The operator attests it, `by_account` points to a clean report, and since the code hash "matches" the guard says allow. Fix: write `by_account` only when the binding is proven. Options: the request was signed by (or `request_review` was paid from) the `deployed` account itself, or the host verifies a reproducible build (`cargo near build reproducible-wasm` on the CI/host, never in the sandbox) whose sha256 equals `view_account.code_hash`, or NEP-330 `contract_source_metadata` names the repo and commit. Otherwise store the attestation unbound and have the guard return `CONTRACT_NOT_REVIEWED`.
3. **No real ChainPort (W10-10..14).** Add `backend/intake/src/chain/{port.ts,mock.ts}` and `backend/intake/src/chain/adapters/near/{rpc.ts,adapter.ts}` on `near-api-js@7.4.0`:
   - `FailoverRpcProvider([JsonRpcProvider(fastnear), JsonRpcProvider(lava)])`
   - `verifyMessage` from `near-api-js/nep413`, which does `viewAccessKey` plus a `FullAccess` check (verified in `lib/nep413/index.js:229-251`). Keep your own recipient, nonce and account checks, which it does not do.
   - `getTx` = `provider.viewTransactionStatus({txHash, accountId, waitUntil:'FINAL'})`. **The default is `EXECUTED_OPTIMISTIC`** (`lib/index.js:3340`). Require `status.SuccessValue`, no failed `receipts_outcome`, `transaction.signer_id === accountId`, `receiver_id === contractId`, a single `FunctionCall` `request_review` whose args decode to the request hash, and `deposit ≥ price`. Then `callFunction({contractId, method:'get_request', args, blockQuery:{finality:'final'}})`, since the default finality is `optimistic`.
   - Writes use `Account(operatorId, provider, KeyPairSigner)` with a per-key mutex, one retry on `InvalidNonce`, and `FINAL`. For parallelism use `MultiKeySigner` with several FC keys.
   - `NEAR_ADAPTER=mock|testnet` env switch, with the same contract suite run against both.
4. **The production frontend cannot connect or pay, and makes no API call (W11-10..13).** Integrate `@hot-labs/near-connect@0.12.0`, the API client, challenge → sign → create → pay → confirm. See §5 and §6.
5. **NEP-413 signature encoding mismatch.** Per the NEP-413 spec, wallets return `signature` as **base64**. The backend decodes base58 only (`app.ts:129`, `b58decode`), and the mock signs base58 (`mock-wallet.ts:36`). Real wallet signatures would be rejected as `SIG_INVALID`. Accept base64 in the backend and make the mock emit base64.
6. **The client invents the nonce (`wallet.ts:18`).** It must decode the `POST /api/challenge` nonce (base64 → `Uint8Array(32)`) or the backend returns `NONCE_UNKNOWN`.
7. **Fake on-chain verification (W11-15).** Replace `ATTESTED_SHA256` with a read-only `callFunction` view of `get_attestation(request_hash)` on `NEXT_PUBLIC_RPC_URL`, and fetch report files from the reports origin. Remove "Tamper the report" and the Mock `<select>` from production, and extend the bundle guard to fail on `Tamper the report`, `WALLET_REJECT` and constant hashes.
8. **Guard wrapper correctness (W13-09/13).** Use `const v = await lookup(receiverIdOf(action))`. Validate `v.verdict ∈ {allow,warn,block}`, and on anything else or on a throw go to `onWarn` (fail closed to a human). Require `(await onWarn(v)) === true`. Intercept `signAndSendTransaction`, `transfer` and `functionCall`, check every receiver in multi-action transactions, add `GuardBlockedError` and a `.d.ts`, and test warn→true reaches the signer once. In `run.mjs`, guard the **receiver**.

## 5. NEAR integration

### Contract (`contracts/review-registry/src/lib.rs`)
- **near-sdk**: `=5.5.0` with `legacy` and `unit-testing` in prod deps. Current is 5.30.0 (crates.io, also in the local cargo cache). Legacy `collections::LookupMap` and `#[near_bindgen]` still work but are superseded.
- **Storage keys**: `BorshStorageKey` enum `Key{Requests, Attestations, ByAccount, ByRepo}` (`:10-16`) is fine, with no prefix collisions. `by_repo` grows without bound (Gap 10).
- **Payable**: only `request_review` is `#[payable]`. All other methods reject attached deposit by default (good). FC keys cannot attach deposit anyway. No storage accounting (Gap 10).
- **Access control**: `only_owner` and `only_operator` compare `predecessor_account_id` (correct for FC-key callers *if* the key lives on the operator account; it does not in the deploy script, Gap 1). `refund` allows operator or owner (matches spec). There is no `#[private]` callback because there are no callbacks.
- **Events NEP-297**: format correct (`EVENT_JSON:` + standard, version, event, data array). Payloads are thin. There are no events for `mark_running` or `withdraw` and no admin events.
- **Re-entrancy**: no cross-contract calls. Both transfers are fire-and-forget after the state write (`:201-203`, `:216-217`), so there is no re-entrancy window. The residual risk is accounting drift when a transfer fails, because there are no callbacks.
- **Overflow**: `overflow-checks = true` in release, `earned.saturating_add` (prefer `checked_add` + panic, though unreachable in practice), and `withdraw` subtraction is guarded.
- **Owner rotation**: none. `treasury` is immutable, which limits a compromised owner key to sending earned funds to the fixed treasury. A compromised owner can still `set_operator` to itself and attest arbitrary "clean" records, which poisons the guard. Add two-step rotation and consider a multisig owner.
- **Upgrade**: none (deferred). The contract account's full-access key from `create-account` is the de-facto upgrade path, and the deploy script does not remove or document it.

### Client (frontend)
- **NEP-413**: the payload bytes are correct: u32 tag `2147484061`, borsh message, 32-byte nonce, borsh recipient, `None` callback (`nep413.ts:25-30`). It matches the backend (`lib.ts:106-111`), and the e2e proves round-trip verification. But signing is mock-only, the nonce is client-made (Gap 6), and the signature encoding is base58 rather than base64 (Gap 5).
- **Payment tx**: none. The mock returns a random `mock:` hash, which is discarded. Required shape with near-connect:
  ```ts
  const wallet = await connector.wallet();
  const outcome = await wallet.signAndSendTransaction({
    receiverId: env.CONTRACT_ID,               // build-time constant; reject if API's contractId differs
    actions: [{ type: 'FunctionCall', params: {
      methodName: 'request_review', args: { request_hash: requestHash },
      gas: '30000000000000', deposit: priceYocto } }],
  });
  await api.confirmPayment(requestId, { txHash: outcome.transaction.hash });
  ```
  Pin `receiverId` to the build-time `NEXT_PUBLIC_CONTRACT_ID` and refuse a mismatched `contractId` from the API, so a compromised or misconfigured API cannot redirect payment. Persist `{requestId, txHash}` in sessionStorage before calling `/payment`.

### Backend chain adapter
- **Real testnet or mainnet ChainPort**: none. There is no `ChainPort` interface, no RPC client and no `near-api-js` dependency. Payment, request, attest, refund and key permission are all Postgres `mock_*` tables (`store.ts:116-225`).
- **FullAccess via `view_access_key`**: no, it is a `mock_key` table lookup (`app.ts:135`). near-api-js 7.4 `verifyMessage` does this check, but at `optimistic` finality, which is acceptable for a key check.
- **tx status FINAL**: no tx lookup at all. When added, pass `waitUntil:'FINAL'` explicitly (the near-api-js default is `EXECUTED_OPTIMISTIC`) and use `finality:'final'` for `get_request`.
- The NEP-413 crypto itself is correct: sha256(payload) then ed25519 verify (`lib.ts:129-132`), with recipient bound and account and nonce matched (`app.ts:132-134`).

## 7. Quality issues

- **Contract**: legacy collections and `#[near_bindgen]`; `unit-testing` feature compiled into the prod dependency; redundant `state_exists` check; no input validation on attest strings; unbounded `by_repo` Vec; thin events; `saturating_add` hides overflow; error constants are ad-hoc strings (consider `#[derive(FunctionError)]` or a const list shared with the backend).
- **Contract tests**: they assert log substrings, not parsed NEP-297 JSON. They make no receipt or transfer assertions. 4 gate tests are missing (see W10-02/04/05/07).
- **Deploy script**: account and key topology is wrong, syntax is invalid, secrets are printed to the terminal, the method list includes nonexistent methods, there is no build step, and no test asserts the printed commands' consistency.
- **Frontend**:
  - `tsc` fails with 77 errors and no gate runs it.
  - `.ts` import extensions are used without `allowImportingTsExtensions`.
  - `canonical-message.mjs` has no `.d.ts`.
  - Network, recipient and preset are hard-coded.
  - Production ships the mock select, the tamper button and a constant "attested" hash.
  - The UI claims "on-chain attestation" with no chain read.
  - `dist/` is committed.
